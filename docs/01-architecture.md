# 01 — البنية والمراجعة الفنية للنسخة الحالية

> الحالة: وثيقة تصميم معتمدة للتوجه الاستراتيجي (Audit Practice Platform).
> تاريخ الإعداد: أكتوبر 2026 · النسخة المشمولة بالمراجعة: bank-reconciliation-pro 0.2.0 (Stage 2).

---

## 1. الغرض من هذه الوثيقة

توثّق هذه الوثيقة ثلاثة أمور: (أ) نتيجة المراجعة الفنية الفعلية للنسخة الثانية بعد تشغيل الاختبارات والبناء في بيئة نظيفة، (ب) البنية الموجهة للمنصة التي نحوّل إليها المشروع تدريجيًا دون هدم، و(ج) سجلّ المشكلات المعروفة والقرارات المعمارية الملزِمة. أي كود جديد يُكتب بعد تاريخ هذه الوثيقة يجب أن يلتزم بالقرارات في القسم 5، وأي انحراف عنها يتطلب تحديث الوثيقة أولًا ثم الكود.

التوجه المعتمد: تحويل «Bank Reconciliation Pro» إلى منصة إدارة مهام التدقيق الخارجي «Audit Practice Platform»، مع بقاء محرك المطابقة البنكية أول وحدة تحليل محاسبي داخلها. لا مشروع منفصل، ولا إعادة بناء شاملة؛ التطوير تزايدي وكل مرحلة لها بوابة قبول قبل الانتقال لما بعدها.

## 2. نتيجة مراجعة النسخة الحالية (Stage 2)

### 2.1 ما هو موجود فعليًا

| المكوّن | الملف | الوصف |
|---|---|---|
| محرك التحليل والمطابقة | `src/core.mjs` (+ `src/core.d.mts` لأنواع TypeScript) | تطبيع الأرقام العربية/الفارسية، كشف الأعمدة عربي/إنجليزي، تحليل المبالغ والتواريخ، التحقق من الصفوف، مطابقة واحد-لواحد محافظة |
| الواجهة | `src/App.tsx` (ملف واحد) | استيراد CSV/XLSX/XLS/PDF، تعيين الأعمدة، معاينة، تحقق، تشغيل المطابقة، ثنائية اللغة عربي/إنجليزي مع RTL/LTR |
| الاختبارات | `tests/core.test.mjs` | تغطي: تطبيع الأرقام والعناوين، كشف الأعمدة، صيغ المبالغ، التواريخ (ISO / يوم-شهر-سنة / تسلسل Excel)، الصفر قيمة صحيحة، تحويل مدين/دائن إلى صافي موقّع، سلوك المطابقة المحافظة (الربط الدقيق، نافذة التاريخ، عدم المطابقة الآلية للملتبس، رفض اختلاف الإشارة) |
| بيانات تجريبية | `samples/*.csv` | كشف بنك ودفتر أستاذ لسيناريو اختبار يدوي |

نقاط قوة جديرة بالحفظ: المحرك لا يخمّن المطابقات الملتبسة (يُسجّلها فقط)، لا يقبل اختلاف إشارة المدين/الدائن بين المصدرين، يحفظ الصفوف غير القابلة للتحليل ظاهرة للمراجعة بدل تجاهلها، ولا ينفّذ أي قيد محاسبي. هذا التوجه «المحافظة المعلنة» هو أصل استراتيجي للمنصة لأنه يتوافق مع عقلية التدقيق، ويجب ألا يُكسر في أي مرحلة قادمة.

### 2.2 نتائج التحقق البيئي (بوابة المرحلة 0)

شُغّل المشروع في بيئة نظيفة (Node v24.21.0) بالأوامر نفسها:

- `npm test`: **ناجح بالكامل — 14 اختبارًا فريدًا، 0 فشل**.
- `npm run build`: **ناجح** (`tsc -b && vite build`)، حزمة الإنتاج تولّد بلا أخطاء.
- `npm audit`: **ثغرتان عاليتا الخطورة** (تفصيلهما في §2.4).

> **ملاحظة حول فرق العدد (23 مقابل 14):** في جهاز المكتب ظهر 23 اختبارًا لأن `node --test` اكتشف ملف الاختبار مرتين وأعاد تنفيذ الاختبارات التحليلية التسعة مرتين (يُظهر سجل التنفيذ في النسخة المحلية بلوكين متطابقين). السلوك غير مؤذٍ نتيجيًا لكنه يجعل عدد الاختبارات مؤشرًا غير موثوق في بوابة القبول. الإصلاح: تثبيت أمر الاختبار على المسار الصريح في `package.json` — `"test": "node --test tests/"` — بحيث يكون الاكتشاف حتميًا في أي بيئة. هذا تغيير سطر واحد يُنفَّذ مع أول دفعة كود في المرحلة 0.

### 2.3 تقييم معماري سريع

1. **المحرك معزول تمامًا عن الواجهة** (`core.mjs` لا يعرف شيئًا عن React) ويعمل في Node والمتصفح معًا. هذا هو الموضع الصحيح ليبقى «محرك التدقيق المشترك» في الطبقات الجديدة.
2. **الحالة كلها داخل الذاكرة**: البيانات المستوردة ونتائج المطابقة تُخزّن في `useState` وتفقد عند إعادة تحميل الصفحة. هذا مقبول كنموذج استعراضي، لكنه أول عائق أمام أوراق العمل وسجل الاستثناءات — لا يمكن توثيق أي شيء لا يبقى.
3. **`App.tsx` ملف واحد بأدوار متعددة** (تحليل PDF، OCR، إدارة الحالة، العرض). التوسّع يتطلب تقسيمه، لكن ليس كعمل مستقل الآن: التقسيم يُنفَّذ مع إدخال طبقة البيانات (المرحلة 1→2) لأن اختبارات المحرك وحدها لا تحمي مسارات الاستيراد في الواجهة.
4. **المحرك بلغة `.mjs` مع أنواع يدوية في `.d.mts`**. النسخ المقبلة ستضيف كيانات ومفاهيم كثيرة (استثناء، ورقة عمل، مراجعة)؛ الحفاظ على ملفي أنواع متوازيين يصبح عبئًا. القرار: المحرك يهاجر تدريجيًا إلى TypeScript ملفًا ملفًا مع كل وحدة تُعدَّل، دون تغيير سلوكه (الاختبارات الحالية هي صمام الأمان).
5. **استيراد PDF يعتمد إحداثيات النص** (`transform[4/5]` مع مسافة فاصلة ثابتة 32px) وهو استدلال هشّ يختلف بين البنوك؛ التوثيق الحالي للقيود في README ممتاز ويُنقل كما هو إلى سجل المشكلات.

## 3. البنية الموجهة: ثلاث طبقات + عقد واحد

```
┌─────────────────────────────────────────────────────────────┐
│  طبقة الواجهة (React + Vite)                                │
│  عرض عربي/إنجليزي · تعيين الأعمدة · أوراق العمل · المراجعة   │
└──────────────────────────┬──────────────────────────────────┘
                           │ عقد أنواع TypeScript صريح
┌──────────────────────────▼──────────────────────────────────┐
│  محرك التدقيق المشترك (Engine) — مستقل عن React وطبقة التخزين │
│  الاستيراد والتحليل · المطابقة · كشف الاستثناءات · العينات     │
│  الموجود اليوم: core.mjs (أول وحدة)                          │
└──────────────────────────┬──────────────────────────────────┘
                           │ واجهات المستودعات (Repositories)
┌──────────────────────────▼──────────────────────────────────┐
│  طبقة البيانات (Data Layer) — قابلة للتبديل                  │
│  الوضع المحلي: SQLite (مشفَّرة لاحقًا) + ملفات الأدلة على القرص │
│  الوضع السحابي: API + PostgreSQL معزول لكل مكتب              │
│  المزامنة: صريحة، مرئية للمستخدم، مبنية على سجل التغييرات     │
└─────────────────────────────────────────────────────────────┘
```

**العقد الوحيد الذي يربط الطبقات هو «ملف مهمة التدقيق» (Engagement File).** كل بيانات مستوردة، وكل مطابقة، وكل استثناء، وكل دليل، وكل مراجعة، تُعرَّف دائمًا ضمن مهمة (`engagement_id`) تنتمي لعميل (`client_id`) ينتمي لمكتب (`firm_id`). لا أداة «معزولة» تنشئ بيانات خارج هذه السلسلة. هذا القرار هو حمايتنا من إعادة البناء لاحقًا عند دخول المستخدمين والصلاحيات والسحابة، لأن العزل والصلاحيات والمراجعة كلها تعلق على هذه السلسلة الجاهزة منذ اليوم الأول.

قواعد الطبقات:

1. المحرك لا يقرأ ولا يكتب في التخزين مباشرة؛ يستقبل بيانات ويعيد نتائج. الواجهة — عبر طبقة المستودعات — هي من يحفظ.
2. كل نتيجة محرك (مطابقة، استثناء، تحذير) تحمل مرجعها للبيانات المصدرية (دفعة/سطر) — التتبع العكسي مبدأ تصميم لا ميزة إضافية.
3. ملفات العملاء الحساسة لا تُرفع تلقائيًا لأي سحابة؛ الرفع فعل صريح يبدأه المستخدم ويظهر في واجهة المزامنة مع سجل كامل.
4. أي حساب يتم داخل الواجهة (وليس في المحرك) يُعد دَينًا تقنيًا يجب نقله للمحرك؛ الواجهة تعرض ولا تستنتج.

## 4. المحلي والسحابي: قرار الجمع

تطبيق واحد، قاعدة كود واحدة، محرك واحد. الفرق بين الوضعين يُحصَر في طبقة البيانات:

| البعد | الوضع المحلي (افتراضي) | الوضع السحابي (اختياري) |
|---|---|---|
| قاعدة البيانات | SQLite على جهاز/شبكة المكتب | PostgreSQL معزول لكل مكتب (صفوف مكتب معزولة منطقيًا كحد أدنى، قاعدة مستقلة كخيار مؤسسي) |
| ملفات الأدلة | مجلد محلي مضبوط بمسارات نسبية + تجزئة SHA-256 للتحقق | تخزين كائنات مع تشفير ومفاتيح مدارة |
| هوية المستخدم | ملف تعريف محلي (اسم + رمز PIN) تُربط به سجلات المراجعة والتغيير | مصادقة مركزية |
| المزامنة | لا شيء يخرج افتراضيًا؛ صندوق الصادر (Outbox) يسجل ما يحتاج مزامنة | دفع/جلب صريح يعتمده المستخدم، بمعالجة تعارض مُعلنة |
| النسخ الاحتياطي | ملف قاعدة + مجلد أدلة مضغوطان ومشفَّران، مع اختبار استعادة دوري | نسخ آلية مع اختبار استعادة موثق |

لا تُعتبر المنصة آمنة تجاريًا لمجرد أن المعالجة داخل المتصفح: التخزين المؤقت للمتصفح، وسجلات الأخطاء، والنسخ الاحتياطية، وآلية المزامنة — كلها تدخل نطاق الاختبار الأمني قبل أي تسويق (بوابة المرحلة 7).

## 5. القرارات المعمارية الملزِمة (ADRs)

| # | القرار | السبب |
|---|---|---|
| ADR-1 | «ملف مهمة التدقيق» هو جذر التجميع (Aggregate Root): لا بيانات خارج سلسلة `firm → client → engagement` | يمنع خلط ملفات العملاء ويجعل الصلاحيات والعزل والمراجعة قابلة للتركيب من اليوم الأول (بوابة قبول المرحلة 2) |
| ADR-2 | المعرفات UUIDv7 تُولَّد في الطرف المحلي | تعمل دون اتصال، بلا تصادم عند المزامنة، ومرتبة زمنيًا تسهّل الفهرسة والتتبع |
| ADR-3 | المحرك وحدة JS/TS مستقلة (لا React ولا DOM)، وظل `core.mjs` هو بذره | قابل للاختبار في Node، قابل لإعادة الاستخدام (محليًا/سحابيًا/تحزيم سطح مكتب مستقبلًا) |
| ADR-4 | المطابقات المقترحة آليًا ليست حقائق؛ لا تصبح معتمدة إلا بقرار مستخدم مسجَّل (من/متى/بأي معطيات) | مبدأ المحافظة المحاسبي الحالي + متطلب قابلية التتبع |
| ADR-5 | سجل التغييرات (Change Log) بأسلوب الإضافة فقط (append-only) لكل فعل على كيان، بمعرّف الفاعل والجهاز | العمود الفقري للثقة محليًا وسحابيًا، ومتطلب التوثيق المهني (ISA 230) |
| ADR-6 | المبالغ تُخزَّن وحدات صغرى صحيحة `amount_minor` + عملة؛ التفاوت يُحسب على الوحدات الصغرى | يلغي أخطاء الفاصلة العائمة في المقارنات والفروقات |
| ADR-7 | الأدلة والمستندات المرفقة ثابتة بعد الإرفاق (immutable)؛ التعديل = دليل جديد يُلغي سابقًا برابط | ملف التدقيق يجب أن يثبت ما كان مرئيًا يوم إجراء الاختبار |
| ADR-8 | المخطط القياسي لقاعدة البيانات هو DDL محمول واحد (`db/schema.sql`) يعمل على SQLite محليًا وPostgreSQL سحابيًا | يمنع انفلاق مخططين متباعدين مع تقدّم المزامنة |
| ADR-9 | وحدة واحدة تُنفَّذ في كل مرة، مع اختبارات معروفة النتائج قبل الانتقال | منهجية العمل المعتمدة؛ لا استثناءات حتى لو بدا التغيير صغيرًا |

## 6. حدود الإصدار الحالي (معلنة بوضوح)

- لا طبقة تخزين دائمة بعد؛ «الحفظ» اليوم = ذاكرة الصفحة فقط.
- المطابقة واحد-لواحد فقط: التجميع والتجزئة ورسوم البنوك وفروق العملة والعمليات المعكوسة لا تُعالَج بعد — كلها في خطة المرحلة 1.
- استخراج PDF الأفضل-الممكن غير موثوق لإعادة بناء الأعمدة المالية بين البنوك، وOCR يعيد نصًا غير منظّم؛ كلاهما موثق في README ويبقى كذلك حتى تُبنى اختبارات اصطناعية لكل نمط بنك.
- لا مستخدمون ولا صلاحيات ولا كيانات مكتب/عميل بعد — وثائق التصميم (02 و03 و04) تحدد ذلك قبله، والتنفيذ يبدأ بترتيب المراحل.

الخطوة التنفيذية التالية بعد اعتماد هذه الوثائق: تنفيذ KI-5 ثم KI-1 ثم KI-2 كوحدات صغيرة مختبرة (إغلاق ملف الاعتمادات)، ثم بناء طبقة المستودعات + حقول المزامنة القياسية فوق المخطط المعتمد في `db/schema.sql` — دون ربط أي بيانات حقيقية قبل اعتماد التصميم.
