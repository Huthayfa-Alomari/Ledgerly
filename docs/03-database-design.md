# 03 — تصميم قاعدة البيانات وطبقة التخزين

> المخطط التنفيذي: `db/schema.sql` (المرجع الملزم). هذه الوثيقة تشرح القرارات خلفه وسياسة تشغيله محليًا وسحابيًا. لا يُكتب أي كود استيراد أو حفظ قبل اعتماد هذا المخطط.

---

## 1. الاستراتيجية العامة

**مخطط واحد محمول، محرّكان تشغيليان.** الملف `db/schema.sql` هو المصدر الوحيد للحقّ؛ يُنفَّذ كما هو على SQLite (الوضع المحلي) وعلى PostgreSQL (الوضع السحابي) لأنه كُتب بجمرة SQL قياسية مع تعليقات تبيّن الفروق. هذا يمنع المبدأ الأخطر في المشاريع المزدوجة: انفلاق مخططين متباعدين يصبحان نظامين مختلفين.

| القرار | الاختيار | السبب |
|---|---|---|
| القاعدة المحلية | SQLite (ملف واحد على جهاز/شبكة المكتب) | تعمل دون خادم، نسخ احتياطي بسيط (ملف)، ناضجة ومدعومة |
| القاعدة السحابية | PostgreSQL | سلامة معاملات قوية، أنواع JSONB وفهارس، مناسبة لعزل المكاتب |
| المعرّفات | UUIDv7 مخزّنة نصًا (TEXT) | تُولَّد محليًا دون اتصال، لا تصادم عند المزامنة، مرتبة زمنيًا تفيد الفهرسة والتتبع |
| المبالغ | `INTEGER` وحدات صغرى (`amount_minor` = هللات/سنتات) + `currency` | لا فاصلة عائمة في أموال؛ المقارنات والفروقات صحيحة بالضبط (ADR-6) |
| التواريخ | `TEXT` بصيغة ISO (`YYYY-MM-DD` للحقول اليومية، طابع UTC كامل للطوابع) | متوافقة مع محرك المطابقة الحالي (نفس صيغة `parseDate`) وقابلة للنقل بين القاعدتين |
| البيانات المرنة | `TEXT` بصيغة JSON على SQLite / `JSONB` على Postgres | حفظ السطر الأصلي `raw_json` ومعطيات التشغيل وتحذيرات التحليل دون أعمدة متفرقة |
| الملفات | خارج القاعدة دائمًا: مسار نسبي + `sha256` داخل صف `evidence` | القاعدة تبقى صغيرة وقابلة للنسخ؛ الدليل يتحقق تكامله من التجزئة |

## 2. حقول المزامنة القياسية (تُكرَّر في كل جدول أعمال)

```sql
firm_id        TEXT NOT NULL,      -- العزل (أول عمود بعد id دائمًا)
created_at     TEXT NOT NULL,      -- طابع UTC
created_by     TEXT,               -- user id (NULL مسموح فقط في بذور النظام)
updated_at     TEXT,
updated_by     TEXT,
row_version    INTEGER NOT NULL DEFAULT 1,   -- يزيد 1 عند كل تعديل
origin_device  TEXT,               -- معرف التثبيت المحلي المولّد للصف
deleted_at     TEXT,               -- حذف منطقي (tombstone للمزامنة)؛ NULL = حي
```

القواعد:

1. **`row_version` شرط التحديث:** كل UPDATE يتضمن `WHERE id = ? AND row_version = ?` ويزيده — يمنع الاطواء الصامت على تعديل آخر ويكشف التعارض عند المزامنة بدل دفنه.
2. **التعارض عند المزامنة يُعرض ولا يُحل آليًا:** لا «الأخير يفوز». عند اكتشاف نسختين لنفس الصف، تُعرض للمستخدم مقارنة صريحة ويُسجَّل قراره في `change_log`.
3. **الحذف منطقي فقط:** `deleted_at` يموّه الصف من الواجهة ويبقيه لسجل التغييرات والمزامنة. الحذف الفيزيائي غير موجود في هذا المخطط (استثناء وحيد: تنظيف ملفات مؤقتة وليست أدلة).
4. **صندوق الصادر (Outbox):** جدول `sync_outbox` يُعبأ من كل عملية كتابة عبر مشغل أو من طبقة المستودعات مباشرة، ويمثل «ما ينتظر مزامنة». المزامنة تستهلكه صراحة؛ لا شيء يغادر الجهاز خلفيةً دون رؤية المستخدم.

## 3. سجل التغييرات

جدول `change_log` إضافته فقط (append-only): ممنوع UPDATE/DELETE عليه في أي صلاحية (يُفرض بمنع منح الإذن سحابيًا وبقاعدة محلية لا توفر مسار كتابة ثانوي). كل فعل يكتب: الفاعل، الجهاز، نوع الكيان ومعرفه، لقطة `before/after`، السبب الاختياري، و`sync_batch_id`. هذا الجدول هو: أداة التوثيق المهني (من فعل ماذا ومتى)، وأساس المزامنة (نقل الأحداث لا الحالات)، وأداة التحقيق عند أي شك.

## 4. الفهارس والقيود (موجودة في `db/schema.sql` بالتفصيل)

- فهرس على `(firm_id, engagement_id)` في كل جدول تدقيق — مسار الاستعلام الأساسي (فتح ملف مهمة وكل محتوياته).
- فهرس فريد `(engagement_id, reference)` على `working_paper`، و`(client_id, start_date)` على `fiscal_year` (منع التداخل يتحقق إضافيًا في الكود لأن SQLite لا يدعم قيد استبعادًا)، و`(engagement_id, code)` على `account`.
- مفاتيح خارجية مع `ON DELETE RESTRICT` للحفاظ على السلسلة `firm→client→engagement` (الحذف الفيزيائي ممنوع عمليًا بهذا التصميم).
- قيود CHECK على تعدادات الحالة (`status IN (...)`) كي لا يدخل صف بلا آلة حالة.

## 5. سياسة الهجرات (Migrations)

1. المجلد `db/migrations/` يحمل ملفات مرقمة تسلسليًا: `0001_initial.sql` ثم `0002_*.sql`... (المخطط الأصلي `schema.sql` يُولَّد منه أو يُجمَّع منه).
2. جدول `schema_version` يسجل الهجرة المطبقة ووقتها.
3. الهجرات تُطبَّق عند بدء التطبيق (محليًا) أو نشرًا (سحابيًا)، وهي للأمام فقط؛ التراجع يُنفَّذ بالنسخ الاحتياطي لا بهجرة عكسية.
4. قاعدة: أي هجرة تُختبَر على نسخة بيانات اصطناعية كاملة قبل الدمج، ونجاح `npm test` شرط.

## 6. التشفير والنسخ الاحتياطي (التزامات المرحلة 7 مسبقة التصميم)

- **تشفير أثناء التخزين:** قاعدة SQLite عبر SQLCipher (أو مكافئ) بمفتاح يستخرج من PIN/مفتاح المكتب — القرار النهائي مع المرحلة 7، لكن المخطط لا يفترض أبدًا قراءة مباشرة لأي سر من القاعدة (لا كلمات مرور نصية: `auth` بجدول منفصل وبلمسات تجزئة).
- **تشفير أثناء النقل:** TLS إلزامي في أي وضع سحابي؛ لا مسار مزامنة بلا TLS.
- **إدارة المفاتيح:** مفتاح التشفير لا يُخزَّن في القاعدة نفسها ولا في الكود؛ فصل مفاتيح لكل مكتب.
- **النسخ الاحتياطي:** نسخة مضغوطة مشفّرة من (ملف القاعدة + مجلد الأدلة) بجدول دوري، مع **اختبار استعادة فعلي موثق** — النسخة غير المُختبرة الاستعادة لا تُعد نسخة احتياطية.
- **العزل:** كل استعلام يمر عبر طبقة المستودعات التي تُلحق `firm_id` حسب المستخدم الحالي — لا استعلامات SQL حرة من الواجهة. حتى في الجهاز المحلي يُحاكى نطاق «المستخدم الحالي» كي يعمل كود الصلاحيات كما سيعمل سحابيًا.

## 7. طيّ الحالية (Current State Mapping)

محرك المطابقة الحالي `core.mjs` ينتج بنى في الذاكرة: `{matches, ambiguous, unmatchedBank, unmatchedLedger, summary}`. خريطة حفظها في المخطط:

| بنية المحرك الحالية | الصف المقابل في المخطط |
|---|---|
| ملف مستورد (صفوف + تعيين أعمدة + تحذيرات) | `import_batch` + `transaction_line` (لكل صف، مع `raw_json`) |
| تنفيذ `matchTransactions` بمعطياته | `reconciliation_run` (مع `params_json`) |
| عنصر في `matches` | `match` بحالة `suggested` (تتحول `approved` بقرار) |
| عنصر في `ambiguous` | `exception` بنوع `ambiguous_candidates` |
| عنصر في `unmatchedBank/unmatchedLedger` | `exception` بنوع `unmatched_bank` / `unmatched_ledger` |
| تحذيرات `validateRows` | `exception` بنوع `unparseable_row` / `validation_warning` مرتبطة بـ `import_batch` |

هذه الخريطة هي عقد الوحدة الأولى للمرحلة 1: «الحفظ والتتبع» — تنفَّذ كوحدة واحدة باختبارات معروفة النتائج (استيراد عينة، تشغيل مطابقة، إعادة تحميل، التحقق من بقاء النتائج وسجل التغييرات) قبل أي شيء آخر.

## 8. ما لا يفعله هذا التصميم عمدًا

- **لا أعمدة مالية عامة بلا عملة:** لا يوجد حقل مبلغ بلا `_minor` + `currency` مرافقة.
- **لا علاقات عابرة للمكاتب:** لا يوجد أي `JOIN` مشروع بين `firm_id` مختلفين؛ حتى الربط الأفقي `cross_link` محصور بمهمة واحدة.
- **لا «مزامنة ذكية» خفية:** لا حل تعارض آليًا ولا رفع تلقائي للملفات — القرارات الصعبة تُعرض للمستخدم.
- **لا حذف فيزيائي لأدلة أو أوراق عمل أو سجلات:** حتى لو طلب المستخدم؛ يوجد «إلغاء/استبدال» فقط.
